\section{Product Choice}

\begin{itemize}
    \item \textbf{Product Name:} Meal Slots
    \item \textbf{Repo URL:} https://github.com/rithikkulkarni/csc-510-proj-3
\end{itemize}

We chose this product because it's an inventive idea that feels like a software someone might use and because we saw potential in it to expand and innovate. In addition, Meal Slots uses some powerful infrastructure that felt interesting to learn to access and maintain, and the code was well-maintained and hadn't rotted as much as the other projects we attempted.

Those other projects were Epicourier (Section 1 Group 12, Github Repo here), SafeBites (Section 1 Group 5, Github Repo here), and Route Dash (Section 1 Group 28, Github Repo here), ReqTrace (Section 1 Group 29, Github Repo here), and Taste Buddiez (Section 1 Group 22, Github Repo no longer available). Each of those projects had succumbed to code rot much more than Meal Slots; Taste Buddiez no longer had an accessible repository, Route Dash and ReqTrace had many libraries and APIs that needed to be connected to, and Safe Bites and Epicourier weren't able to be launched. Ultimately, Meal Slots suffered the least code rot and thus was the best software to use.

\section{Use Cases}

\subsection*{Spin for a Meal}
{\footnotesize
\begin{supertabular}{@{}p{0.26\linewidth}p{0.68\linewidth}@{}}
\textbf{Name} & Spin for a meal \\
\hline
\textbf{Primary actor} & Player (Guest or Authenticated User) \\
\hline
\textbf{Stakeholders \& interests} & Player: wants a fast, low-effort meal decision. \\
\hline
\textbf{Preconditions} & App is loaded; dish catalog is populated; spin cooldown has elapsed. \\
\hline
\textbf{Trigger} & Player clicks "Spin". \\
\hline
\textbf{Main success scenario} & 1. Player selects a category for each of the three slots (or picks a preset).\newline
2. Player optionally sets allergen filters and Power-Ups.\newline
3. Player clicks Spin.\newline
4. System fetches eligible dishes per slot, honoring category, tag, and allergen filters.\newline
5. System runs a weighted random selection per slot, respecting any locked slots.\newline
6. System displays the three chosen dishes.\newline
7. System starts a cooldown before another spin is allowed. \\
\hline
\textbf{Extensions} & 4a: No category resolved for a slot $\rightarrow$ system rejects the spin with "category is required"; player picks a category and retries.\newline
4b: No dishes match the active filters for a slot $\rightarrow$ system fills that slot with a "No options" placeholder dish instead of failing.\newline
5a: A slot was locked, but the locked dish no longer matches the current filters $\rightarrow$ system silently drops the lock and selects a new dish for that slot.\newline
5b: Player re-spins with identical filters and reel contents within the same 10-second window as the prior spin $\rightarrow$ the weighted-random seed repeats and the same result is returned.\newline
6a: The spin request errors on the server $\rightarrow$ system shows placeholder results; player may retry.\newline
7a: Player clicks Spin again before the cooldown expires $\rightarrow$ the control is disabled and no request is sent. \\
\hline
\textbf{Postconditions} & Three dishes are displayed for the round; a spin record is logged best-effort; any still-valid locks are retained for the next spin. \\
\end{supertabular}
}

\begin{supertabular}{@{}p{0.26\linewidth}p{0.68\linewidth}@{}}

\hline
\textbf{Primary actor} & Party Member \\
\hline
\textbf{Stakeholders \& interests} & Host --- executes the group's decision. Other members --- want their vote to count toward the outcome. \\
\hline
\textbf{Preconditions} & The party has completed a group spin; player is a connected member. \\
\hline
\textbf{Trigger} & Member clicks "Keep" or "Reroll" on a slot. \\
\hline
\textbf{Main success scenario} & 1. Member views the current dish in a slot.\newline
2. Member clicks "Keep" or "Reroll".\newline
3. System records the member's vote for that slot.\newline
4. System tallies live votes against currently connected members.\newline
5. When "keep" votes reach a majority of connected members, system locks that slot automatically.\newline
6. When "reroll" votes instead reach a majority, system triggers the host to re-roll just that slot.\newline
7. The updated slot state is broadcast to all members. \\
\hline
\textbf{Extensions} & 2a: Member changes their vote before quorum is reached $\rightarrow$ the previous vote is replaced by the new one.\newline
4a: A voting member disconnects $\rightarrow$ once their heartbeat times out, they are dropped from the live count used for quorum, which can shift the threshold needed. \\
\hline
\textbf{Postconditions} & The slot's lock/reroll state reflects the group's majority decision without the host needing to act unilaterally. \\
\end{supertabular}

3a: A slot is locked $\rightarrow$ the existing dish is retained; only unlocked slots are re-spun.\newline
4a: Internal \texttt{/api/spin} call fails or times out $\rightarrow$ system falls back to a hardcoded menu of 6 dishes.\newline
5a: After 6 attempts, a slot still has no unique dish $\rightarrow$ slot receives a "No options" placeholder. \\
\hline
\textbf{Postconditions} & Three unique, allergen-safe dishes are selected and displayed to all members \\
\end{supertabular}

\textbf{Postconditions} & No authenticated session remains in the current browser context and prior account data is not exposed. \\
